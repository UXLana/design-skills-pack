# Case-study handoff and interactive evidence

Use only what the requested handoff needs. Do not turn a writing task into a prototype rebuild.

## Current handoff

Honor an existing user-designated draft inbox. Put the narrative and receiving instructions there;
identify any supporting artifacts that remain elsewhere so the receiving agent can resolve them.
Preserve the material's disclosure boundary when moving it into a repo.

Record the requested output and status; the authoritative narrative and private evidence location;
the approved exhibit set; the receiving repo/route if relevant; the material permitted at each
destination; verification revision/date; meaningful remaining work; and the next action.

Keep private capture separate from the presentation draft. Research supports context only to the
extent its sources warrant. Internal links and sensitive notes do not automatically belong in
receiving-repo files or public copy. A documented reported outcome remains attributed.

For a bundle transfer, include filenames, schema/version and hashes when useful to distinguish it
from older packages. State which files can be committed and which require protected storage. Provide
restart instructions and clearly label development-only settings when handing off a local preview.

## Selecting coded exhibits

Before using a prototype as evidence, identify its story purpose, source revision and entry route.
Verify the interface against the author's distinguishing description, not just a similar project name.
Record whether it is approved, superseded or excluded. Distinguish an actual earlier version from
scenario presets or loading/empty/error states. Retain excluded work in the permitted private record.

Keep both the original source provenance and later replay adaptations identifiable. A modified replay
is not evidence that the original product shipped that combination of screens or behavior.

## Synthetic walkthroughs

For the promised walkthrough, record route/action coverage, fixture relationships, total/status/date
consistency, simulated actions and reset behavior. An empty service-dependent page is not a usable
demo. Unverified or unsupported actions belong in the handoff as gaps; do not claim complete coverage.
Avoid live external actions or real customer data in a synthetic replay.

If opening-screen previews are requested, use captures of the selected current entry state after
shell and data changes. Retain the necessary application header/context, relevant prototype toolbar
and a visible return to the case study. When standalone and embedded modes are supplied, verify both.
These are functional preview requirements, not a prescription for the case-study page's visual layout.

A later source, fixture, entry-state or shell change can invalidate screenshots and earlier checks.
A source edit also does not update a previously built package automatically. Mark affected artifacts
stale, name what must be rebuilt or checked, and keep historical results tied to their revisions.

## Receiving website work

When implementation is authorized, inspect the receiving repo's current route, approved components,
theme and content contract. Reuse the approved visual design. The case-study skill does not prescribe
art direction or placement of text, images or prototypes.

When implementation is outside scope, finish with usable copy, artifact references and known limits.
Configuration, hosting and publication remain receiving-repo work; do not undertake them solely
because they appear as future steps in the handoff. Honor existing authorization without asking again.
